# 大面积补全的技术路线与选型（RORem 调研）

> 写于 2026-09-26。起因：用户问「方向是否可以朝向大面积识别发展」。
> 结论先行：**可以，但必须换模型；LaMa 在这个区间已经到头了。**

> **关于配图**：本文提到的实验对照图（原在 `docs/rorem_probe/`、`docs/structure_probe/`）
> 未纳入仓库 —— 这些实验是在单张实拍照片上跑的，产出图等于原片的局部放大。
> 实验的**数据和结论都完整保留在正文**，不影响阅读。

## 一、为什么 LaMa 在大面积区间到顶了

昨天（09-25）的分频带实测给了判决性证据：

| 频带 | 保留率 |
|---|---|
| **低频（结构/明暗）** | **54%** ← 掉得最多 |
| 中低频（大纹理） | 99% |
| 中频（纹理细节） | 104% |
| 中高频（细纹） | 85% |
| 高频（颗粒） | 81% |

**这不是「补得不够好」，是「没有信息可用」。**

LaMa 属于**单步前馈**的 inpainting 网络，它学的映射是「(带洞图, mask) → 完整图」。
给定一个巨大的空洞，它没有任何机制去「推理」墙后面该有什么结构 ——
它能做的只有顺着边界颜色平滑地内插。

空洞越大 → 可依赖的边界像素越远 → 越退化成纯色/线性渐变。
这就是低频保留率只有 54% 的机理，也是人眼读作「糊」的真正原因。

**关键判断：这是模型固有能力边界，不是调参能解决的。**
所以 v0.02 里做的颗粒再注入（针对高频）投入产出比很低，已默认关闭。

## 二、要解决大面积，需要什么能力

大空洞补全本质是一个**生成**任务，不是**插值**任务。需要：

1. **语义先验** —— 知道「这是一面墙」才知道该怎么延伸
2. **迭代修正** —— 一步步去噪，每一步都能看全局（扩散模型天然具备）
3. **可控性** —— 能通过提示词或参考图引导生成方向

扩散模型（Diffusion）在这三点上全面强于前馈网络。
但**通用扩散 inpainting 未必赢 LaMa** —— 09-25 的调研数据：

| 模型 | LPIPS（越低越好） |
|---|---|
| LaMa | **0.135** |
| FLUX-Inpainting | 0.145 |
| SD-Inpainting | 0.183 |

所以在扩散模型里，还得选**专门为「移除」训练**的那一类。

## 三、候选模型对比（实测核查数据）

| 模型 | 底座 | 权重体积 | 许可 | 8G 显存 | 可用性 |
|---|---|---|---|---|---|
| **RORem** | SDXL-Inpainting | 6.6 GB | **Apache 2.0** | 勉强可跑 | ✅ **选它** |
| ObjectClear | SDXL-Inpainting | 类似 | ⚠️ NTU S-Lab，仅非商用 | 同 | ❌ 许可不符 |
| GeoRemover | 自研 two-stage | 未知 | 未发布权重 | - | ❌ 暂无权重 |
| FLUX ObjectRemoval | FLUX | 24 GB+ | 非商用 | ❌ 爆显存 | ❌ |

### 为什么是 RORem

1. **许可干净（Apache 2.0）** —— cleanplate 是 MIT 开源，不能引入非商用权重。
   这一条直接淘汰了效果更好的 ObjectClear。
2. **专门为移除训练** —— 用 20 万对「物体存在 / 物体移除」的配对数据
   微调 SDXL-Inpainting。配对数据是关键：它学会了「移除」而不是「补全」，
   避开了自监督训练范式下「把物体又画回来」的歧义。
3. **成功率实测领先** —— 论文报告比前作提升 18%+，
   512 分辨率成功率 76.2%、1024 分辨率 70.2%。
4. **有 LCM 蒸馏版** —— `RORem-LCM` 只要 4 步推理，同样 Apache 2.0，
   速度可提升一个数量级（质量略降）。

### 权重明细（实测 HF API）

```
4897.3 MB  unet/diffusion_pytorch_model.safetensors   ← 主体
1325.0 MB  text_encoder_2/model.safetensors
 234.7 MB  text_encoder/model.safetensors
 159.6 MB  vae/diffusion_pytorch_model.safetensors
总计 6620 MB
```

**注意：没有 fp16 变体**，repo 里只有全精度。要靠 `torch_dtype=float16` 加载时转换。

**静态显存估算**：UNet 4.9G × 0.5 (fp16) ≈ 2.45G
\+ text_encoder_2 0.66G + text_encoder 0.12G + VAE 0.08G ≈ **3.3G 权重**，
加激活约 4G。**8G 显存够用，不必 cpu offload。**

## 四、核心工程难点：512 vs 4648×7502

RORem 官方推理代码写死了：

```python
input_image = load_image(input_path).resize((resolution, resolution))
```

**如果照搬，等于把 4648×7502 的照片压成 512×512 再补，比 LaMa 现在更糊。**

### 解法：沿用已有的「分区域推理」思路

我们 v0.01 已经为 LaMa 解决过一次同样的问题（整图缩放 → 只裁 mask 区域）。
这次照搬同一策略：

```
原图 4648×7502
  ↓ 取 mask 的 bbox，外扩 35% 做上下文
裁剪区域（比如 1800×1400）
  ↓ 长宽比保持，缩到目标分辨率（512 或 1024）
送 RORem 推理
  ↓ 结果按比例放大回裁剪区域尺寸
贴回原图（只在 mask 内合成）
```

这样模型看到的是**接近原始像素密度**的内容，而不是被压扁的整图。

**已知风险**：放大回去这一步仍然要插值（从 512 放大到 1800 是 3.5 倍），
细节会有损失。缓解办法是**用 1024 分辨率**（RORem-mixed 版支持），
放大倍率降到 1.76 倍，损失小得多。

**待验证**：1024 下显存是否还够。

## 五、验证计划（脚本：`scripts/probe_rorem.py`）

三个问题按顺序回答，每步都能独立中止：

| 阶段 | 命令 | 回答的问题 |
|---|---|---|
| env | `--stage env` | 依赖齐吗？镜像通吗？显卡认吗？ |
| fetch | `--stage fetch` | 6.6G 要下多久？ |
| run | `--stage run --res 512` | 跑得动吗？多快？质量如何？ |
| run | `--stage run --res 1024` | 1024 下显存够吗？质量提升多少？ |

脚本设计原则：
- **不 import app，不碰 engine.py** —— 纯测量，验证失败零污染
- 缓存走 `HF_ENDPOINT=https://hf-mirror.com`（实测直连 HF 不通、代理未必常开）
- 显存不够自动降级：attention slicing → vae slicing → cpu offload
- 输出对照图到 `docs/rorem_probe/`（该目录未纳入仓库），附高频能量比值指标

## 八、RORem 实测结果：**不通过**（2026-09-26 补）

三阶段验证全部跑完（`scripts/probe_rorem.py`），结论是 **RORem 不能直接用于本项目**。

### 实测数据

| 分辨率 | 步数 | 加载 | 推理 | 显存峰值 | 结果 |
|---|---|---|---|---|---|
| 512 | 20 | 72s | **12.3s** | 7.51G / 8G | 跑通，质量差 |
| 1024 | 30 | 76s | **31.7s** | **9.59G** ⚠️ | 跑通但**溢出到共享内存** |

速度其实达标了（用户预期 30 秒~1 分钟，1024 用 31.7s）。
**卡住的是质量与架构，不是速度。**

### 三道过不去的坎

**1. 语义不匹配 —— 它学的是「删除物体」，我们要的是「保留主体、只补背景」**

第一次测试把 mask 放在画面中央，RORem **忠实地把中间的人抹掉了**（头部、手、
衣服糊成一团）。这不是 bug，是它被训练的目标：给定 mask 就把里面的东西消失掉。

我们的场景里，用户涂的往往**紧贴主体**（去掉人旁边的伞），
RORem 会顺手把主体边缘也重绘掉。

**2. 全图重绘 —— 与「选区外 bit 级不变」的底线直接冲突**

观察 1024 的输出：**不只是 mask 内被改，整个裁剪区域的衣服、裙子都变了**。
这是 SDXL inpaint 的固有机制（`strength=0.99` 几乎完全重绘）。

我们项目有条写进 selftest 的铁律：
> 选区外像素必须 bit 级不变。

**RORem 天然违反这条。** 要接就得在外面套一层「结果只在 mask 内 alpha 混合」的
封装 —— 那它补出来的内容质量还要再打折扣（因为它的输出本来就是全图重绘的，
只取 mask 部分等于只用它一半的能力）。

**3. 显存超限**

1024 分辨率下峰值预留 9.59G > 8G 物理显存，已经溢出到共享内存（会大幅降速）。
降到 512 能压进 6.84G 但质量明显不够。

### 决定

**放弃 RORem 集成。** 权重留在 `.hf-cache/rorem`（6.46G），
`probe_rorem.py` 保留作为将来复测的工具，但不接入主流程。

## 九、B 方案实测：低频结构补偿 —— **也不通过**（2026-09-26 补）

RORem 失败后转向零依赖方案：在 LaMa 输出上做低频结构补偿。
实验脚本 `scripts/exp_structure.py`。

### 思路

09-25 实测：LaMa 补全区的**低频结构保留仅 54%~64%**（本次复现：0.64）。
而低频（大范围明暗渐变）看起来**可以从周围外推**。
于是提出：把补全区的低频替换成外推的低频场。

三种外推方法：
- `guided` —— 用 cv2.inpaint 把周围低频填进来
- `multiscale` —— 拉普拉斯金字塔逐级引导填充
- `poly` —— 多项式曲面拟合，用 mask 外的点拟合再外推

### 实测数据（真实 LaMa 输出，mask 占 10.2%）

| 方法 | 补全区结构 | 周围结构 | 比值 |
|---|---|---|---|
| 补偿前（LaMa） | 6.95 | 10.82 | **0.64** |
| guided | 7.30 | 10.82 | 0.67 |
| multiscale | 5.82 | 10.82 | 0.54（更差） |
| poly | 12.81 | 10.82 | 1.18 |

**数字上 `poly` 看起来有效（0.64 → 1.18），但看图就露馅了**：
mask 区域出现了**明显的斜向亮带** —— 那是多项式曲面在边缘过拟合出来的假结构，
不是真实的布料褶皱。

### 为什么这条路走不通

把 mask 区域放大后逐版对比，差异非常清楚（原对照图未纳入仓库）：

- **原图**：蓝色布料，有清晰的**褶皱走向**和**明暗交界线**
- **LaMa 补全**：褶皱**完全消失**，变成一片平滑的蓝
- **补偿后**：要么毫无变化（guided / multiscale），要么凭空造出假结构（poly）

**根本原因：mask 内的真实结构（褶皱走向）信息已经永久丢失。**
周围环境里**没有任何线索**能推断出「这里原本应该有几道褶、往哪个方向走」。

低频外推能补的是**大范围明暗渐变**（天空的渐暗、墙面的明暗过渡），
补不了**结构走向**。而大面积补全最缺的恰恰是后者。

**这与 09-25 的结论完全一致：LaMa 的「糊」是模型能力边界，后处理补不出来。**

### 决定

**不集成。** 实验脚本保留（`scripts/exp_structure.py`），
三种外推方法都不接入主流程。

## 十、累计结论与下一步方向

两条技术路线（换模型 / 后处理补偿）都在 2026-09-26 被实测排除。

**共同的根本原因：大面积补全缺的是「结构生成」，这是生成能力问题，
既不是调参能解决的（后处理路线），也不是搬一个为「删除」训练的模型能解决的
（RORem 路线）。**

真正有价值的方向（尚未验证）：

1. **引导用户分小块修** —— 面积小的时候 LaMa 表现很好（昨天实测的小面积场景）。
   把「一笔圈一大块」的行为在交互上拦住，比在算法上硬扛更实际。
2. **换真正的结构生成模型** —— 需要 SDXL 以上的显存（8G 是硬约束），
   或等更小的专用模型出现。
3. **接受现状** —— 大面积本来就不是这个工具的目标场景。
